# Security and privacy

O Board is a personal system. It is meant to run on your home network, and to be reached from outside only through
Tailscale. This page explains what is protected, how, and where the limits are.

## The Gemini API key

- The key exists in exactly one place: `/etc/oboard/oboard.env` on the Pi.
  - The file is owned by `root:oboard` with mode `0640`, and the installer writes it with `umask 077`.
  - Only root and the server process can read it.
- The key is never sent to the phone, the TV or a browser.
  - It is not in the APK, the web files or any API response. `/api/settings` exposes model names, never the key.
  - Requests to Gemini are made by the server.
- **Gemini Live** needs the phone to talk to Google directly, so the Pi mints a short-lived **ephemeral token** for
  each session instead of sharing the key:
  - it works once;
  - it must be used within 1 minute;
  - it expires after 30 minutes;
  - it is locked to the Live model.

  Even if someone captured it, it cannot be turned into the real key or used for anything else.
- For development, `server/.env` can hold a key. It is gitignored. Do not copy it to the Pi; use the installer.

## Who can use the board: pairing and tokens

- Every client (phone, browser, TV) holds its own random **256-bit device token**.
  - The server stores only its SHA-256 hash, so a copy of the database does not reveal usable tokens.
  - Every API call and the WebSocket require it.
- New devices pair with an **8-digit code** shown on the TV or generated by an already-paired phone. Codes:
  - can be used once;
  - expire after 10 minutes;
  - are rate-limited (8 tries per address per 5 minutes);
  - are all revoked at once if 25 wrong guesses arrive within 10 minutes.
- The TV's own token is created by the server at first start and stored in `/var/lib/oboard/display.token`
  (mode `0600`). The kiosk passes it to the browser through a private file, so it never appears in the process list.
  Pairing cannot create a display token.
- On the phone, the token is encrypted with an **AndroidKeyStore** AES-GCM key that cannot be exported. App data is
  excluded from cloud backup (`allowBackup=false` plus data-extraction rules).
- **Removing a device** (Settings → Connection) revokes its token and cuts its open live connection at once. Forget
  the Pi on the phone to wipe its token.

## Network exposure

- The Pi serves **plain HTTP** on port 8080. This is a deliberate trade-off for a home device: there is no trusted
  certificate for `192.168.x.x`. It is acceptable because:
  - on your home network, the token is still required for everything;
  - away from home you use **Tailscale**, where all traffic is encrypted end to end (WireGuard) and only your own
    devices can connect.
- **Do not port-forward 8080 to the internet.** Over plain HTTP on the open internet, a token could be read in transit.
- The Android app allows cleartext HTTP (`network_security_config.xml`). Android cannot say "only for private
  addresses", and the Pi's address may be a LAN IP, a Tailscale `100.x` IP or a `.local` name. The app only ever
  talks to the Pi you paired with, and to model-download hosts over HTTPS.
- `/api/me` lists the Pi's addresses so the phone can switch networks. Only paired devices can see this list.
  `/api/info` (used during discovery) shows only an id, the version and whether a key is set.
- Avahi announces `_oboard._tcp` on the local network so the app can find the Pi. Anyone on your Wi-Fi can see that an
  O Board exists, but cannot use it without pairing.

## Browser and server hardening

- Web pages are served with a strict Content-Security-Policy:
  - `script-src 'self'`, with no inline scripts and no third-party code;
  - `frame-ancestors 'none'`, which stops clickjacking.

  They also send `X-Content-Type-Options: nosniff`.
- Uploaded files are stored by content hash and served with `nosniff` and a sanitised filename. Requests are
  size-limited (`MAX_UPLOAD_MB`, default 40).
- The assistant's tools validate every argument against the same schema as manual edits. The AI cannot write
  arbitrary data or touch other tables.
- Destructive AI actions need a fresh confirmation from you, and every AI change can be undone.
- systemd sandboxes the server:
  - a dedicated `oboard` user, with no shell and no capabilities;
  - `ProtectSystem=strict`, so it can only write `/var/lib/oboard`;
  - `NoNewPrivileges`, private `/tmp`, kernel protections;
  - a memory cap.
- Node.js is pinned to one version, and the download is verified against a SHA-256 before installing.

## Widgets and their API keys

Widgets are code written by the assistant, so they are treated as untrusted:

- **Sealed frame.** Each widget runs in an iframe sandboxed without same-origin. It cannot read the board page, the
  device token, cookies or storage.
- **No network.** The frame's policy has `connect-src 'none'`, so `fetch`, `XMLHttpRequest` and `WebSocket` are
  blocked. It also cannot load outside scripts. Data only comes through `ob.fetch`, which the board page relays to the
  Pi.
- **The proxy refuses your home network.** It will not fetch from private, loopback, link-local or CGNAT/Tailscale
  addresses. This is checked when the name is resolved (and on every redirect), so a widget cannot reach your router,
  the Pi or other devices.
- **Keys never enter the widget.** Widget code uses a placeholder like `{{FINNHUB_KEY}}`. The Pi fills it in:
  - only for the website the key was saved for (e.g. `finnhub.io` and its subdomains);
  - only over https;
  - never inside a host name.

  A widget that tries to send the key elsewhere gets an error. On a redirect to another website, key-carrying headers
  are dropped.
- **Storage.** Keys are stored in `/var/lib/oboard/secrets.json` (mode `0600`, readable only by the service).
  - They are not in the database, backups or exports.
  - They are never returned by the API; the app only sees names and websites.
  - They never appear in the conversation, so they are not sent to Gemini.
  - The TV cannot add or remove keys.
- **Entering keys.** When the assistant needs a key, it asks for one with `request_api_key`. A card appears in the app,
  and the key goes from that card straight to the Pi. The assistant is instructed never to ask for a key in chat.
- **Limits.** The proxy enforces a request rate, a 2 MB answer cap and timeouts. Destructive edits by the assistant,
  including deleting a widget, still need your confirmation, and every change can be undone.

After restoring a backup onto a new Pi, add your widget keys again: they are deliberately not part of backups.

## Supply chain

| Component | Protection |
|---|---|
| Server | One npm dependency (`ws`), with a lockfile |
| Web UI | No dependencies from a CDN; everything is bundled. Chart.js (for widgets) is vendored after checking npm's integrity hash |
| Android speech library (sherpa-onnx AAR) | Fetched from its official GitHub release and checked against a pinned SHA-256 |
| Speech models on the phone | Each download is checked against a pinned SHA-256 from the publisher. One small tokenizer file has no published hash and is size-checked |

## What goes to Google

| Mode | Sent to Gemini |
|---|---|
| Typed or on-device voice (default) | The text of your message, recent conversation on that board, a summary of the board, and any images you attach |
| Gemini Live | Your microphone audio for the duration of the session, plus the same board context |

On-device speech recognition and the voice run on the phone: in the default mode, no audio leaves it. Your boards are
stored only on your Pi. Gemini's data use is governed by your Google AI Studio terms (paid and free tiers differ).

## Release signing

The APK is signed with `android/oboard-release.jks`, created by `scripts/make-keystore.ps1`. That file and
`android/keystore.properties` are gitignored. **Back them up privately.** Android only accepts updates signed with the
same key; if the key is lost, future versions must be installed fresh, after uninstalling.
